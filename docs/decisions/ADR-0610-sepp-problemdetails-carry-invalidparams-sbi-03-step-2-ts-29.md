## ADR-0610: SEPP ProblemDetails carry invalidParams (SBI-03 step 2, TS 29.500 Table 5.2.7.2-1 NOTE 1)

**Date:** 2026-11-21. **Status:** Proposed.

**Context.** ADR-0607 (step 1) gave sbi-core a way to put `invalidParams` in a ProblemDetails and
left every NF unchanged. This is step 2 for one NF, the SEPP (`nfs/sepp`). Two tables of TS 29.500
V19.7.0 apply:

- Table 5.2.7.2-1 (NF as HTTP server), NOTE 1: "'invalidParams' attribute shall be included in
  the 'ProblemDetails' data structure indicating unsupported, missing or incorrect IE(s) or query
  parameter(s) or 3gpp-Sbi-Discovery-* header(s)." TS 29.573 V19.7.0 (`specs/3gpp/29573-j70.docx`)
  points its three SEPP services at it: clauses 6.1.6.2 (N32-c handshake) and 6.2.6.2 (N32-f JOSE
  forwarding) say protocol error handling "shall be supported as specified in clause 5.2.7.2 of
  TS 29.500", 6.3.5.2 (Nsepp_Telescopic_FQDN_Mapping) says "clause 5.2.7 of TS 29.500", and
  6.1.6.3 / 6.2.6.3 / 6.3.5.3 say the common application errors of Table 5.2.7.2-1 may be used.
- Table 5.2.7.4-1 (errors generated by the SCP/SEPP, clause 5.2.7.4), NOTE 1: "'invalidParams'
  attribute shall be included in the 'ProblemDetails' data structure indicating unsupported,
  missing or incorrect IE(s) or 3gpp-Sbi-Discovery-* header(s)." The same seven 400 causes carry
  it there (plus `INVALID_DISCOVERY_PARAM`, which the SEPP never sends), and its
  `MANDATORY_IE_MISSING` / `MANDATORY_IE_INCORRECT` rows describe an IE "within an HTTP header".
  This covers the SEPP's own forwarding refusals on 3gpp-Sbi-Target-apiRoot.

TS 29.573 adds no N32-specific rule for these causes. Its one invalidParams rule is for
`POLICY_MISMATCH` on N32-f (clause 6.2.4.2.2, Table 6.2.4.2.2-2, and 5.5.3.2.1 / 5.5.3.2.2: "may
include the invalidParams attribute indicating which IEs were received ciphered ..."), which is not a NOTE 1 cause and is out
of scope here (see Disclosed).

**Decision:** 11 of the SEPP's 12 NOTE 1 answers carry `invalidParams` (ADR-0607 builders); status
codes, causes, titles and details are unchanged. The 12 sites are main.cpp 8 and n32.cpp 4; each
one whose parameter the code knows names it:

| Site | Cause | `param` |
| --- | --- | --- |
| `n32.cpp` `negotiate`, targetPlmnId of another PLMN | OPTIONAL_IE_INCORRECT | `/targetPlmnId` |
| `n32.cpp` `negotiate`, n32HandshakeId not 16HEXDIG | OPTIONAL_IE_INCORRECT | `/n32HandshakeId` |
| `n32.cpp` `exchange_params`, n32fContextId not 16 hex digits | MANDATORY_IE_INCORRECT | `/n32fContextId` |
| `n32.cpp` `exchange_params`, neither cipher suites nor policy | MANDATORY_IE_MISSING | `/jweCipherSuiteList`, `/protectionPolicyInfo` |
| `main.cpp` n32f-process, no metaData in the reformatted message | MANDATORY_IE_INCORRECT | `/reformattedData/aad` |
| `main.cpp` N32-f over TLS, no target apiRoot | MANDATORY_IE_MISSING | `header 3gpp-Sbi-Target-apiRoot` |
| `main.cpp` N32-f over TLS, target not in this PLMN | MANDATORY_IE_INCORRECT | `header 3gpp-Sbi-Target-apiRoot` |
| `main.cpp` telescopic mapping, both or neither query parameter | INVALID_QUERY_PARAM | `query foreign-fqdn`, `query telescopic-label` |
| `main.cpp` telescopic mapping, foreign-fqdn of this PLMN | INVALID_QUERY_PARAM | `query foreign-fqdn` |
| `main.cpp` NF side, no telescopic FQDN and no target apiRoot | MANDATORY_IE_MISSING | `header 3gpp-Sbi-Target-apiRoot` |
| `main.cpp` NF side, target not in a remote PLMN (from the header) | MANDATORY_IE_INCORRECT | `header 3gpp-Sbi-Target-apiRoot` |

- JSON Pointers are the member names of `TS29573_N32_Handshake.yaml` (`SecNegotiateReqData`:
  `targetPlmnId`, `n32HandshakeId`; `SecParamExchReqData`: `n32fContextId`, `jweCipherSuiteList`,
  `protectionPolicyInfo`) and `TS29573_JOSEProtectedMessageForwarding.yaml`
  (`N32fReformattedReqMsg.reformattedData`, `FlatJweJson.aad`), REL-19 commit bca84b6.
- `sepp::Decision` and `sepp::ParamDecision` (n32.hpp) carry an `invalid_params` list that
  main.cpp passes through; `sepp_n32` now links `sbi_core` for `sbi_core::InvalidParam`.
- Each entry has a `reason` naming what was wrong (e.g. "must be 16 hexadecimal digits").
- The n32f-process site names `/reformattedData/aad`: metaData travels inside `aad` (a
  base64url-encoded DataToIntegrityProtectBlock), so `aad` is the IE of this request body that is
  absent, undecodable or lacks metaData. A pointer into the decoded block would not point into the
  body the peer sent.
- The `MANDATORY_IE_MISSING` of exchange-params names both members. Both are optional in the YAML;
  this SEPP can process the request only with one of them, so both are the missing alternatives.
  The two telescopic-label cases name both query parameters for the same reason, with a reason
  that says whether both were present or both absent.

**Sites left without invalidParams.**

- `main.cpp` n32f-process, the reconstructed request's `requestLine.authority` is not in this
  PLMN (`MANDATORY_IE_INCORRECT`, the ProblemDetails built into the JOSE-protected response to the
  consumer NF). The consumer never sent that IE itself: its SEPP built the authority from a
  3gpp-Sbi-Target-apiRoot header or a telescopic FQDN, and this SEPP cannot tell which. No
  `param` encoding names a URI authority; naming the header would be a guess.
- A branch of a changed site, not a 13th site: `main.cpp` NF side, target not in a remote PLMN
  when the target came from a telescopic FQDN in the request URI: same reason, the four `param` encodings have none for a URI authority. In
  practice a telescopic label maps only to an FQDN this SEPP accepted as another PLMN's.
- Out of scope as ADR-0607 disclosed: the SEPP's `json::parse(...).get<>()` sites answer
  `INVALID_MSG_FORMAT`, not a NOTE 1 cause, so nothing changes there.

**Verified (2026-11-21, master machine, a fresh worktree build at this commit, Debug).** The
targets `sepp`, `sepp_e2e_integration_tests` and `conformance_tests` build with 0 failed steps
(1453 of 1453). `conformance_tests --gtest_filter='SeppN32.*:SbiInvalidParams.*'`: 24 tests, all
passing, the new `SeppN32.Note1RefusalsNameTheInvalidIe` included (the four n32.cpp sites, and
that a non-NOTE 1 refusal carries none). `SeppEndToEnd.Note1ErrorsNameTheInvalidParam` (two real
processes, NRF and SEPP B; covers the NF-side, telescopic-mapping, N32-c exchange-capability and
N32-f-over-TLS sites) builds and is listed by `--gtest_list_tests`, but was **not run** here: it
needs the lab certificates, which this worktree does not have. Not run: the rest of
`conformance_tests`, any other integration binary, a full `ctest`. The n32f-process
`/reformattedData/aad` site and the exchange-params sites are not exercised end to end (the
latter by the conformance test only). CI result to be added.

**Disclosed.**

- `POLICY_MISMATCH` (TS 29.573 6.2.4.2.2, "may include the invalidParams attribute"): not sent with
  invalidParams; `sepp::open` reports a mismatch without the IE list. Not a NOTE 1 cause.
- `MISSING_PARAMETER` (403) is never answered by the SEPP.
- The SEPP's relay of another NF's ProblemDetails is unchanged: it forwards what it gets.

**Rejected alternatives.**

- *Name `/metaData` (or `/metaData/n32fContextId`) for the n32f-process site.* It points into the
  decoded aad, not into the body sent; a JSON Pointer must resolve against the request body.
- *Name `header 3gpp-Sbi-Target-apiRoot` when the target came from a telescopic FQDN, or for the
  reconstructed request's authority.* The header was not the source there; a wrong `param` is worse
  than none.
- *Build the ProblemDetails in n32.cpp.* The pure logic stays free of HTTP; it returns the
  `InvalidParam` list and main.cpp renders it, as it already does with status and cause.
