## ADR-0475: LI increment 7a -- the UDM IRI-POI: event list for approval (TS 33.127 7.2.2.4, TS 33.128 7.2.2.3)

**Date:** 2026-10-09. **Status:** Built and verified end to end through the real udm process (slices 1-4): events 1-4 codecs, the UDM POI (X1/X2 wiring, SUPI/PEI/GPSI target match, registration/deregistration/authentication hooks), and a passing 2-test e2e suite (`li_udm_e2e_integration_tests`). Event 5 stays deferred; events 6/8 out of scope.

**Context.** The LI plan (ADR-0364) step 7 starts with the UDM. TS 33.127 V19.7.0 clause 7.2.2.4 lists the events the UDM/UDR IRI-POI generates xIRI for; TS 33.128 V19.7.0 clause 7.2.2.3 gives each event's record and its M/C/O fields. The UDM is reached by the ADMF over LI_X1 (target identities SUPI, PEI, GPSI, IMPU/IMPI per 7.2.2.2) and sends xIRI over LI_X2 to MDF2, exactly like the AMF POI (ADR-0378/0457) on the shared `libs/li-poi` runtime.

**Event list (TS 33.127 7.2.2.4) with the trigger and the UDM operation that exists in this repo (`nfs/udm`).**

| # | Event / record (TS 33.128) | Trigger (TS 33.128 clause) | This UDM | Proposed |
|---|---|---|---|---|
| 1 | Serving system / `UDMServingSystemMessage` (M: sUPI, servingSystemMethod, roamingIndicator; C: pEI, gPSI, gUAMI, gUMMEI, pLMNID, serviceID) | amf3GPPAccessRegistration / amfNon3GPPAccessRegistration received (Nudm_UECM_Registration, TS 29.503 5.3.2.2.2/.3) | UECM registration exists | **Build** |
| 2 | Start of interception with target already registered / `UDMStartOfInterceptionWithRegisteredTarget` (M: sUPI, uDMSubscriptionDataSets; C: gPSI) | an X1 task activated for a UE that already has a registration context at the UDM | needs the UDM's registration store to be queryable by SUPI | **Build** (mirrors AMF ADR-0461) |

| 8 | ProSe target identifier deconcealment / ProSe target authentication | 5G PKMF / ProSe remote UE | ProSe is not built | **Not applicable now** |

**Proposal (not decided):** build events 1-4 as one increment (3 stages: codecs for the four records from TS33128Payloads, the POI wiring in `nfs/udm` on `li_poi::PoiRuntime`, and an end-to-end test through the real UDM like `test_li_amf_e2e.cpp`), with a SUPI/GPSI/PEI target match and UDM X1 task handling. Events 5, 7 stay open; 6 and 8 are out of scope until the HSS-IWF / ProSe exist.

**Questions for the user.** (a) Approve events 1-4 as the first slice? (b) Event 4: confirm that the authentication record reports only what Table 7.2.2.3.8-1 lists (to be read in full and quoted before coding) and never key material. (c) Event 5: is the UDR change feed (a Nudr subscription) acceptable as the observation point, or should it wait? (d) The UDM instance is single-process with state in the UDR -- LI warrant state follows the AMF POI pattern (in-process, ADMF re-pushes on restart); confirm.

**Disclosed.** TS 33.127/33.128 were read from `specs/3gpp/*.docx` converted to text; only 7.2.2.3.2 and 7.2.2.3.9 were read field by field so far. Other records' fields are NOT yet extracted and nothing here is a design of them.

**Rejected alternatives.** Building all eight events at once (four need interfaces that do not exist here, so they would be untestable stubs). Starting with the SMSF/NEF/CHF POIs (the UDM is the next row in ADR-0364 and its events map onto operations that already exist).

**Status update, slice 1 (2026-10-09).** Event 1 codec built: `UdmServingSystemMessage` (TS 33.128 7.2.2.3, ASN.1 `UDMServingSystemMessage`) in `libs/li-core` (struct, fill/extract, `Event` variant member, encode/decode dispatch); `Xiri.UdmServingSystemMessage*` (2 tests) pass in `conformance_tests` together with the 9 existing Xiri tests. Modelled: sUPI, servingSystemMethod (M); pEI, gPSI, pLMNID, roamingIndicator. NOT modelled: gUAMI, gUMMEI, serviceID. Which of the modelled members are C vs O in the table was taken from the ASN.1 OPTIONAL markers, not from a field-by-field read of the table text. **Not built yet:** the UDM POI itself (X1 listener, X2 client, SUPI/GPSI/PEI target match, hook in Nudm_UECM registration), events 2-4 codecs and triggers, the end-to-end test.

**Status update, slice 2 (2026-10-09).** Event 2 codec built: `UdmStartOfInterceptionWithRegisteredTarget` (sUPI, optional gPSI, `SBIType` reference/value as verbatim UTF-8 strings); round-trip test passes (`conformance_tests` Xiri.*, 12 pass). Which UDM subscription data sets are reported and how their SBI reference/value are rendered is not decided and is a UDM-POI design point still open. Events 3 and 4 codecs, the UDM POI wiring and the e2e test remain.

**Status update, slice 3 (2026-10-13).** Events 3 and 4 codecs built, closing the remaining question (b): Tables 7.2.2.3.4-1 and 7.2.2.3.8-1/-2 were read in full from `specs/3gpp/TS_33.128_j70.txt` before coding -- neither carries key material. `UdmCancelLocationMessage` (ASN.1 `UDMCancelLocationMessage`, CHOICE tag [55]): modelled sUPI, cancelLocationMethod (M), pEI, gPSI, pLMNID (C); NOT modelled (disclosed, same complexity-skip precedent as event 1): gUAMI, aMFDeregistrationInfo, deregistrationData. `UdmUeAuthenticationResponse` (ASN.1 `UDMUEAuthenticationResponse`, tag [110]): modelled sUPI, authenticationInfoRequest (M; itself a nested SEQUENCE -- infoRequestType, authType, servingNetworkName, rGAuthCtx modelled, aUSFInstanceID/cellCAGInfo/n5GCIndicator NOT modelled), aKMAIndicator, authAAA (C); NOT modelled: problemDetails, pvsInfo. `rGAuthCtx` (Mandatory, SIZE(1..MAX), `SubscriberIdentifier` CHOICE of sUCI/sUPI per entry) only models the sUPI alternative -- fill() rejects an empty list, decode rejects a sUCI-typed entry as an error rather than silently dropping it (disclosed limitation, not yet needed: this project has no scenario feeding a UDM authentication-info request keyed by SUCI rather than SUPI). 4 new tests (2 round-trip + malformed-input rejections) pass; `conformance_tests` Xiri.* now 15/15, full suite 492/492. **Not built yet:** the UDM POI itself (X1 listener, X2 client, SUPI/GPSI/PEI target match, hooks in Nudm_UECM registration/deregistration and Nudm_UEAuthentication), the end-to-end test.

**Status update, slice 4 (2026-10-13) -- the UDM POI itself, end to end through the real `udm` process.** `nfs/udm/src/li_poi.{hpp,cpp}` (`udm::UdmLiPoi`, same shared `libs/li-poi` runtime as the AMF/SMF POIs): SUPI/PEI/GPSI target matching (same `bare_identity`/`pei_for_matching` scheme as the SMF POI), an in-process registered-target registry (`note_registered`/`note_deregistered`, the AMF POI's own ADR-0461 pattern reused -- kept decoupled from `AmfRegistrationStore`'s concrete type rather than querying it directly), and the four report_* methods for events 1-4. Wired into `nfs/udm/src/main.cpp`: event 1 at both the 3GPP and non-3GPP-access registration PUT handlers; event 2 via `on_targets_added`, fetching the real am-data from UDR through the existing `fetch_from_udr` lambda (reused, not duplicated) for `uDMSubscriptionDataSets`; event 3 at both Modification PATCH handlers, gated on `purgeFlag == true` (TS 33.128 7.2.2.3.4 bullets 2/3 -- bullet 1, the UDM-initiated DeregistrationNotification, has no client call in this UDM and stays a disclosed gap, same convention as the AMF POI's own ADR-0393 UE-initiated-only note); event 4 at `generate-auth-data`, `infoRequestType` always `Ausf` (that operation's own real definition, TS 29.503 6.3.6.2.2, never guessed per-call), `servingNetworkName` parsed from the real TS 33.501 Annex A.1 SNN string format (a non-matching string skips the event, logged, never fabricates a PLMNID). `config/udm.json` gets a `li_poi` block (disabled by default), mirroring the AMF/SMF/UPF ones. New end-to-end test `tests/integration/test_li_udm_e2e.cpp` (its own binary, `li_udm_e2e_integration_tests` -- same "keep li_core out of the NGAP-linking monolith" reason `li_amf_e2e_integration_tests` is its own binary, ADR-0364): 2 tests, both passing against the real `udm`/`nrf`/`udr` processes -- one drives registration -> purgeFlag deregistration -> generate-auth-data through the real seeded 5G_AKA subscriber (`imsi-999700000000001`) and asserts all three xIRIs (ServingSystemMessage, CancelLocationMessage, UEAuthenticationResponse) land correctly at a loopback MDF2; the other registers first, activates the warrant second, and asserts the StartOfInterceptionWithRegisteredTarget record carries the real UDR am-data as `sbi_value`. No AMF/AUSF/PCF/SMF/UPF/gNB needed -- every UDM event here is triggered by a direct SBI call, not a NAS/NGAP procedure. **Disclosed scope, carried forward:** events 5 and 7 stay open per the approved list; events 6/8 out of scope (no HSS-IWF/ProSe); PEI/GPSI-only-targeted warrants cannot trigger event 2 (the registered-target registry is keyed by SUPI, no live PEI/GPSI -> SUPI resolution exists at hook time); IMPU/IMPI target identities are not modelled anywhere in this project's X1 codec (pre-existing gap, not introduced here).
